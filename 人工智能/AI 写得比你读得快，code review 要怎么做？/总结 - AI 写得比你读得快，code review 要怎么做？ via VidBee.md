Thought for 33 seconds

AI 写代码比人读得快，逐行 Code Review 会成为瓶颈；不读又要人背锅。出路不是发明一种更强的通读方法，而是把 Code Review 拆成三件不同的事，分别处理。

## 三件被捆在一起的事

过去代码产量小，Code Review 同时做三件事：

1. **挑错**：空指针、边界情况等实现错误。
2. **对齐上下文**：改动是否符合架构和业务需求。这部分往往不在代码里，而在记忆、tribal knowledge 和团队潜规则里。
3. **担责**：签字说 ship it，出事由人扛。

AI 把产量拉高之后，三件事不能再捆在一起。读不过来，是因为吞吐量太大；读了看不出错，是因为关键上下文不在 diff 里；不读又怕背锅，是因为签字责任仍在人身上。

## 挑错：交给机器做 double check

人不应重做一遍机器的活，否则人会变成瓶颈；但让机器再算一遍几乎免费，所以挑错应交给机器。

做法是独立复查，而不是自己审自己：写代码的 agent 带着思维惯性，容易为自己的 bug 找理由，要换一个干净的 context 来审。可以两路 AI 各算一遍，再让第三路只标出对不上的地方。Anthropic 的 Claude Code 团队是：提 PR 前先跑本地测试，再用全新上下文的子 agent 复查；PR 之后多组 agent 从不同视角并行找问题，交叉投票后只把真正的问题留给人。机器互审最多三轮，仍不收敛就说明设计有问题，应停下来重做，而不是继续加 scope。

人在这一关的职责是踩刹车，并对没完没了的 scope expansion 说不，同时设计筛选机制，而不是逐行替机器找错。

## 对齐上下文：要 cross check，并把知识写下来

有些问题把代码读一百遍也看不出来。案例：一个改后台会话超时的 PR 过了 CI，AI 和人都没发现问题，上线后企业客户的数据导出大量中断。根因是代码假设所有后台任务都在常规会话里跑完，而六周前针对企业客户的定制已经打破了这个假设，那段改动不在本次 diff 里。

这类核对要脱离代码本身：用数量级是否反常的 sniff test，以及产品历史、上下游变更。AI 当时抓不到，是因为内部文档、产品变更和故障复盘没给它；而这些若只存在于人脑、Slack 私信或无记录的会议里，AI 永远看不见。

规律是：人凭记忆做的 cross check，一旦写成文档，下一次就变成机器可执行的 double check。人负责的边界不是固定的，文档化越多，能交给 AI 的就越多，人就不必原地盯细节。

## 担责：推不走，但签字的含义变了

出事必须有人对业务和客户负责。AI 不能道歉、赔钱或接受降职。Anthropic 在签字关定了三条：

- Agent 不算 approver，多少模型赞成都不能代替人签字。
- 批准只对那一个 commit 有效，再提交就要重看。
- 指挥 agent 写代码的人必须在签字名单上。

签字不再表示“我逐行读过、确认实现无误”，而是“我核对过这次改动的意图、假设和设计”。实现是否正确交给测试和仿真。Anthropic 重写 Git 的 Scion 就是这么用的：从更高层看改动想干什么、是否符合惯例、会不会碰到奇怪的 corner case。

面对超大吞吐（其 monorepo 每天约三万个变更），还要分级：文档、功能开关等低风险变更，测试全过且作者在可信名单内，可免签字直接上线；常规业务逻辑和系统提示词要一人签；核心高危路径和难恢复的关键配置要两人签。少审的前提是能快速回滚。Scion 甚至先合入、不等 CI 跑完，挂了再用二分找到改动并撤回。Claude Code 仓库跑这套流程四个月：合入 PR 增加一倍以上，回滚比例下降约 40%。

## 马上能做的四件事

不必上 Scion，也不必自建大系统：

1. **先写验收标准再派活**：什么叫“对”必须人先想清楚，这是 AI 替代不了的。
2. **不要让刚写完代码的 AI 审自己**：新开干净上下文，或两路赛马对结果。
3. **有意识积累自己的 sniff test**：常看的口径、常见模式、故意埋的会挂输入。
4. **先保证能快速回滚**（报表也先给小范围看、能迅速改），再逐步减少逐行阅读。

## 始终留在人身上的三件事

边界可以一直外推，但这三样推不走：动手前定义什么叫正确；交付时签上名字、出事背锅；还没写下来的规则和直觉，继续写成文档，让机器下次能用。
